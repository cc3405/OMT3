# OMT3 全面审查与整改台账（2026–2027）

> 审查日期：2026-10-30（CST）
> 审查范围：仓库可读取的项目文档、ESP32-S3 固件、替代算法及测试；结合当季 Problem 1、Program Guide 与 General Clarifications 做规则风险核对。
> 审查性质：静态审查与整改建议，不是赛事官方裁定、工程认证或实物验收。
> 状态原则：没有测试记录、照片/视频或可复核数据的项目，不得标记为“通过”。

## 1. 结论摘要

项目已有机械/电气构想、ESP32-S3 bring-up 固件骨架、替代算法和部分测试，但**目前不能认定整套方案已符合比赛要求，也不能认定具备参赛级可靠性**。当前更准确的定位是“有条件可行的原型规划阶段”。

最重要的六项阻塞：
1. 乘坐式车辆的结构承载、重心/倾覆、制动、乘坐者支撑和硬件急停没有实物证据。
2. 整车及运输容器尚未按 Program Guide 门口净空要求完成通过性验证；BOM 中车宽上限 800 mm 不能作为通过证明。
3. 清单交接时序需按 2026-10-01 官方澄清 B9c 修订：计时开始后，必须在车辆越过起始线前交给车辆操作员。
4. 独立卸载装置仍停留在概念/设计阶段，未证明能按题面要求连续卸下三件物品。
5. 购物车挂接、牵引、释放、返区及最终停车未形成完整且重复验证的闭环。
6. 参赛组别、成本口径、完整演出/风格和赛前提交材料仍需确认。

## 3. 子系统审查

### 3.1 乘坐式车辆

现有 BOM 的底盘板、JGB37 电机、驱动轮、万向轮和 2020 型材只是候选物料，不能推断能够安全承载乘坐者。冻结前必须确定乘坐者最大设计质量、车辆自重、载荷分布、支撑面、轮距/轴距、重心高度、倾覆边界、驱动轮/减速箱承载能力、制动距离及急停断能方式。未经成人工程审查和低速安全验证，不得让队员乘坐试车。

### 3.2 门口通过性

Program Guide 的门口要求是通行开口约 28 × 78 in。应以完整装配状态（含购物车/容器、突出件和可拆件的比赛状态）实测；必要时按规则允许的方向转向通过。BOM 中“车宽≤800 mm、建议≤760 mm”不是充分条件，尤其 800 mm 大于约 711 mm 的开口窄边。

### 3.3 购物车

BOM 同时出现商用 60L 购物车及多种挂接/释放物料，存在方案重复和接口未冻结风险。应先选定唯一购物车架构，再画接口控制图。必须验证满载重心、防倾覆、牵引摆振、释放速度/方向、返区轨迹、最终停车和快拆误触发时的安全状态。

### 3.4 独立卸载装置

独立卸载台应作为独立设备验收，而不是车载机构的附件。可考虑独立底座、定位支撑、手动推板/夹持机构、侧挡、止挡和接收托盘；具体尺寸须依据三件实际道具的外形、质量、材质及题面动作确定。至少记录：与车辆无机械/电气连接；装置独立落地；操作方式符合组别对应题面；三件物品全部进入结账区；连续 10 轮测试成功率和失败原因；夹手、滑落、倾倒风险检查。

### 3.5 ESP32-S3 固件

当前 `firmware/esp32_s3/esp32_s3.ino` 是 bring-up/串口点动骨架，包含短时点动、A 相编码器计数、超声波近距停止和限位输入读取。静态代码审查发现：
- 编码器只用 A 相，不能可靠判定方向；未形成速度/距离闭环。
- 限位开关目前主要读取/显示状态，尚未形成完整运动方向互锁。
- 超声波触发停止后，逻辑上的 armed 状态仍需重新审查，避免误认为故障已锁定。
- 尚无完整自动路线、返航、停靠、车载操控、机械臂控制、购物车释放、购物状态机和故障人工复位流程。
- 串口点动骨架不能作为比赛操作系统完成度证明。

以上是源码静态审查结论，不代表已在实物上复现或测试。

### 3.6 电气安全

- ESP32-S3 GPIO 是 3.3V 逻辑；HC-SR04 Echo 等 5V 信号必须做电平适配。
- 急停应有硬件切断驱动能量的路径，不得只调用软件停止函数。
- 电机与舵机电源分路，按实际驱动器拓扑设计共地。
- 保险丝、线径和电源按堵转/峰值电流及实测工况选择。
- 上电、复位、通信丢失、传感器断线、限位触发和 MCU 卡死均须定义并验证安全状态。

### 3.7 替代算法

`tools/substitution.py` 目前实现同类别、预算内最低价候选选择，并以 ID 排序保证同价结果确定性；无候选时返回需人工协助。现有 6 个单元测试覆盖基础场景，但该模块不感知真实库存、不控制机器人，也不等于购物流程已实现。下一步需增加多商品累计预算、助理批准、数据来源校验和整机接口测试。

## 4. 验收表必须同步修订

`docs/ACCEPTANCE.md` 的 R-01 应以如下文字为准：

> 计时开始后，购物清单必须在车辆越过起始线之前交给车辆操作员；通过连续录像确认交接发生在越线之前。

此外应明确独立卸载（规则合规）与卸载重复性（工程可靠性）是两个不同验收目的；购物车释放后的返区必须单列验收；门口通行必须按完整装配状态单列验收。

## 5. 文档与仓库治理

- README 的 D5/3组路径须按实际仓库树逐项验证；不能因为某次读取失败就删除或改动保护区材料。
- `docs/REQUIREMENTS_D5.txt` 若仍为乱码，应重建 UTF-8 可读版本；需求内容必须来自官方题面，不从乱码猜测。
- BOM 当前是采购准备资料，不是可直接下单的冻结清单；在 CAD、道具尺寸/质量、电流数据和成本表完成前，不得标记采购冻结。
- 保留官方文件原始版本和下载日期；官方澄清更新后重新执行规则追踪。
- 代码/文档/测试状态分开标记：源码存在≠构建通过；测试文件存在≠测试运行通过；概念图存在≠实物通过。

## 6. 建议执行顺序

1. **规则冻结**：确认 Division；归档当季 Program Guide、Problem 1 和最新澄清；修正规则追踪表。
2. **尺寸与安全冻结**：门口通行、乘坐支撑、载荷/重心/制动、整车外廓。
3. **机械冻结**：唯一购物车架构、唯一释放方案、独立卸载台总装图。
4. **电气冻结**：依据数据表和实测确定电源、驱动、保险丝、线径及硬件急停。
5. **软件实现**：车载操作、闭环、状态机、故障锁定、订单/替代流程。
6. **整机验证**：模块→子系统→全流程；保存视频、数据、版本、操作者和签字。
7. **赛前资料**：成本、外部援助、解题明细表、风格表、演出脚本和最终清单。
